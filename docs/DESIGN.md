# เอกสารออกแบบระบบแชทธีม MMORPG

สถานะ: ผู้ใช้ให้ทำต่อแล้ว เวอร์ชันในเครื่องผ่าน build, 15 กลุ่มทดสอบ และ Docker smoke ดูผลล่าสุดใน [VALIDATION.md](VALIDATION.md) และบันทึกใน [WORKLOG.md](WORKLOG.md)  
ปรับปรุงล่าสุด: 2 พฤศจิกายน 2026

## 1. เป้าหมาย

สร้างเว็บแชทสำหรับโปรเจกต์ Socket Programming โดยให้ประสบการณ์เหมือนหน้าต่างแชทในเกม MMORPG มี World Chat, Guild Chat และ Private Chat พร้อมระบบล็อกอิน

เอกสารนี้ใช้บันทึกสิ่งที่คุยกันและวางโครงระบบ ผู้ใช้ให้กลับมาเริ่มพัฒนาแล้ว ปัจจุบันมีเวอร์ชันรันในเครื่อง พร้อม README และผลตรวจใน [VALIDATION.md](VALIDATION.md) ส่วนการใช้งานบนโฮสต์จริงและ AI ด้วย key จริงยังไม่ผ่านการทดสอบ

## 3. ข้อกำหนดจากโจทย์

อ้างอิงไฟล์โจทย์และแม่แบบ Implementation Explanation ที่อยู่ในโฟลเดอร์หลักของโปรเจกต์

| ข้อ | สิ่งที่ระบบต้องรองรับ | แนวทางออกแบบ |
| --- | --- | --- |
| R1 | แสดงสถาปัตยกรรม อธิบายโปรโตคอล และใช้ client บนคอมพิวเตอร์จริงอย่างน้อย 2 เครื่อง | เบราว์เซอร์แต่ละเครื่องเชื่อมต่อเซิร์ฟเวอร์กลาง |
| R2 | ข้อความแชทระหว่าง client กับ server ใช้ Socket Programming | ส่งข้อความผ่าน WebSocket |
| R3 | แต่ละ client มีชื่อไม่ซ้ำกัน | ตรวจสอบชื่อที่เซิร์ฟเวอร์และฐานข้อมูล |
| R4 | เห็นรายชื่อผู้ใช้ออนไลน์ทั้งหมด รวมตัวเอง | แสดงรายชื่อผู้เล่นออนไลน์และอัปเดตเมื่อเชื่อมต่อ/หลุด |
| R5 | แต่ละบทสนทนาส่วนตัวและแต่ละกลุ่มมีห้องของตัวเอง | ใช้ room ID แยกกัน |
| R6 | แต่ละห้องมีช่องพิมพ์และพื้นที่แสดงข้อความ | เปิดแต่ละห้องแล้วเห็นประวัติและช่องส่งข้อความ |
| R7 | ส่งข้อความส่วนตัวถึงคนในรายชื่อได้ เห็นเฉพาะผู้ส่งและผู้รับ | เซิร์ฟเวอร์ส่งข้อมูลเฉพาะสมาชิกสองบัญชี |
| R8 | สร้างกลุ่มได้ โดยเริ่มจากมีผู้สร้างคนเดียว | สร้าง Guild แล้วเพิ่มเฉพาะผู้สร้าง |
| R9 | ทุกคนเห็นกลุ่มทั้งหมดและรายชื่อสมาชิกของแต่ละกลุ่ม | มีหน้าหรือแผงค้นหากิลด์และดูสมาชิก |
| R10 | ผู้ใช้เลือกเข้ากลุ่มเอง ห้ามเพิ่มคนอื่นอัตโนมัติ | ใช้ปุ่มเข้าร่วม ไม่เพิ่มสมาชิกแทนผู้อื่น |
| R11 | ส่งข้อความในกลุ่มที่ตนเข้าร่วมได้ สมาชิกเท่านั้นที่เห็นข้อความ | ตรวจสอบสมาชิกทั้งตอนอ่านประวัติและส่งข้อความ |

Part 1 ต้องครบก่อนประเมิน Part 2 และ Part 2 ต้องครบก่อนประเมิน Part 3 จึงควรทำ R1–R11 ให้ครบก่อนเพิ่มฟีเจอร์พิเศษ

Part 3 มีคะแนนพิเศษ 4 ฟีเจอร์ และอย่างน้อยหนึ่งฟีเจอร์ต้องเป็น AI ส่วนการขึ้น cloud เป็นทางเลือกตามโจทย์ แต่ผู้ใช้ยืนยันให้เวอร์ชันแรกเข้าใช้งานผ่านอินเทอร์เน็ตได้แล้ว ยังไม่ได้เลือกผู้ให้บริการโฮสต์

## 4. ประสบการณ์ใช้งานที่เสนอ

รายละเอียดที่ระบุในหัวข้อ 2 ได้รับการยืนยันแล้ว รวมโครงหน้าจอหลัก ส่วนสี ฟอนต์ ระยะห่าง และกติกาย่อยที่ระบุว่าเป็นข้อเสนอยังปรับได้

### 4.1 หน้าต่างแชทแบบ MMORPG

- ใช้บรรยากาศหน้าต่างแชท Ragnarok เป็นต้นแบบ ผสมกรอบและรายละเอียดพิกเซลย้อนยุค โดยออกแบบองค์ประกอบของโปรเจกต์เอง
- มีแท็บ World / Guild / Private ที่สังเกตได้ชัด
- แชทเป็นพื้นที่หลัก แสดงบทสนทนาห้องเดียวที่เลือกอยู่ ไม่รวมข้อความต่างห้องในหน้าต่างเดียว และมีตัวเลขยังไม่อ่านบนรายการห้องอื่น
- หัวห้องแสดงชื่อช่องหรือคู่สนทนาและข้อมูลสมาชิก
- พื้นที่ข้อความแสดงชื่อผู้ส่ง เวลา และเนื้อหา พร้อมเลื่อนดูข้อความเก่า
- ช่องพิมพ์อยู่ด้านล่าง พร้อมปุ่มส่งและสถานะการเชื่อมต่อ
- มีแผงรายชื่อผู้เล่นออนไลน์ กดชื่อเพื่อเริ่มคุยส่วนตัวได้
- กิลด์มีรายการห้องของตัวเอง และมีทางเข้าไปดูรายชื่อกิลด์ทั้งหมด
- เลือกรูปตัวละครพิกเซลจากชุดภาพของโปรเจกต์ ไม่มีหน้าหรือปุ่มอัปโหลดรูป
- รายการกิลด์แสดงชื่อ คำอธิบาย เจ้าของ รายชื่อสมาชิก และปุ่ม Join/Open ไม่เพิ่มตรากิลด์ในเวอร์ชันแรก
- ส่งข้อความด้วย Enter และขึ้นบรรทัดใหม่ด้วย Shift+Enter รองรับข้อความและอีโมจิ โดยยังไม่มีการตอบกลับข้อความ
- เน้นคอมพิวเตอร์ แต่ต้องใช้งานบนมือถือได้ด้วย ข้อเสนอการจัดจอเล็กคือพับแผงรายชื่อและรายการห้องให้เปิดผ่านปุ่ม

เลือกธีมย่อยพิกเซลย้อนยุคและเกมต้นแบบ Ragnarok แล้ว ส่วนสี ฟอนต์ และระดับการตกแต่งยังปรับได้ UI ใช้ภาษาอังกฤษทั้งหมด รวมปุ่ม แบบฟอร์ม ข้อผิดพลาด และสถานะระบบ ตัวข้อความแชทยังรองรับภาษาไทย จึงควรมีฟอนต์ข้อความที่อ่านง่ายรองรับ Unicode และใช้ฟอนต์พิกเซลเฉพาะจุดที่เหมาะสม

### 4.2 เส้นทางใช้งานหลัก

1. เปิดเว็บ → สมัครบัญชีหรือเข้าสู่ระบบ
2. เข้าสู่หน้าต่างแชท → เห็นรายชื่อคนออนไลน์รวมตัวเอง
3. เลือก World → กดเข้าร่วมครั้งแรก → เริ่มสนทนา
4. เลือก Guild → สร้างกิลด์ หรือดูรายการแล้วกดเข้าร่วมเอง
5. เลือกผู้เล่น → เปิดห้อง Private ของคู่นั้น → ส่งข้อความ
6. ออกจากระบบ → ปิดสิทธิ์ใช้งาน session นั้นและอัปเดตสถานะออนไลน์

ยืนยันให้ผู้ใช้สมัครสมาชิกได้เอง ใช้ชื่อผู้ใช้และรหัสผ่านโดยไม่ใช้อีเมล และใช้ชื่อผู้ใช้เป็นชื่อตัวละครที่ไม่ซ้ำกัน ยังไม่รวมระบบกู้รหัสผ่านผ่านอีเมลในขอบเขตนี้

### 4.3 กติกาของแต่ละช่อง

| ช่อง | ใครเห็นรายการห้อง | ใครอ่านข้อความได้ | วิธีเข้าห้อง |
| --- | --- | --- | --- |
| World | ผู้ใช้ที่ล็อกอินทุกคน | ผู้ที่กดเข้าร่วมแล้ว | กดเข้าร่วมด้วยตัวเองครั้งแรก |
| Guild | ผู้ใช้ที่ล็อกอินทุกคน พร้อมดูรายชื่อสมาชิกได้ | สมาชิกกิลด์นั้น | สร้างกิลด์เอง หรือกดเข้าร่วมเอง |
| Private | เฉพาะคู่สนทนา | เฉพาะผู้ส่งและผู้รับ | เริ่มคุยจากรายชื่อผู้เล่น |

World เป็นห้องส่วนกลางที่ระบบเตรียมไว้ แต่ให้กดเข้าร่วมก่อนเพื่อรักษาหลักการเข้ากลุ่มด้วยตัวเอง ส่วน Guild รองรับหลายกิลด์ต่อบัญชี โดยผู้ใช้เลือกแนวทางนี้แล้ว รายละเอียดตำแหน่งปุ่มและการจัดหน้าจอยังปรับได้

### 4.4 วงจรของ Guild

สิ่งที่ยืนยันแล้ว:

- ผู้ใช้สร้างกิลด์ได้ โดยเริ่มจากมีผู้สร้างคนเดียว
- ผู้เล่นเลือกเข้าร่วมกิลด์เอง และเป็นสมาชิกหลายกิลด์ได้
- เมื่อเข้าร่วมแล้ว อ่านประวัติทั้งหมดของกิลด์ได้ รวมข้อความก่อนเข้าร่วม
- สมาชิกออกจากกิลด์ได้ และเจ้าของยุบกิลด์ได้
- มีระบบโอนเจ้าของกิลด์ตามคำขอเพิ่มเติมของผู้ใช้

กติกาย่อยที่เสนอให้ใช้ แต่ยังไม่ได้ยืนยัน:

- เมื่อออกจากกิลด์ ให้เพิกถอนสิทธิ์อ่านประวัติ ค้นหา สรุปด้วย AI และรับข้อความใหม่ทันที รวมทุกแท็บของบัญชีนั้น ข้อความที่ผู้ใช้เคยอ่านหรือบันทึกไว้แล้วไม่สามารถเรียกคืนได้
- ประวัติข้อความที่สมาชิกเคยส่งยังคงอยู่หลังออกจากกิลด์
- เจ้าของโอนตำแหน่งให้สมาชิกปัจจุบันคนอื่นได้ หลังโอนเจ้าของเดิมยังเป็นสมาชิกธรรมดาและออกได้ตามปกติ หากยังเป็นเจ้าของต้องโอนหรือยุบก่อนออก ไม่ปล่อยกิลด์ที่ไม่มีเจ้าของ
- เซิร์ฟเวอร์ตรวจว่าเฉพาะเจ้าของปัจจุบันเท่านั้นที่โอนได้ ผู้รับเป็นสมาชิกอยู่แล้ว และห้องยังไม่ถูกยุบ ทำการเปลี่ยนเจ้าของใน transaction เดียวเพื่อป้องกันคำขอพร้อมกัน ไม่ใช้การโอนเป็นช่องทางเพิ่มสมาชิกอัตโนมัติ
- ก่อนยุบกิลด์มีข้อความยืนยัน หลังยุบห้องหายจากรายการและส่งข้อความไม่ได้ ส่วนการเก็บหรือลบประวัติในฐานข้อมูลยังต้องตกลง

### 4.5 โครงหน้าจอและองค์ประกอบ

ส่วนที่เลือกแล้วนำมาจัดเป็นหน้าจอหลักต่อไปนี้ ตำแหน่งย่อยยังเป็นข้อเสนอสำหรับออกแบบภาพจริง

| หน้าจอ/แผง | องค์ประกอบหลัก |
| --- | --- |
| Sign In / Create Account | ชื่อผู้ใช้ รหัสผ่าน ปุ่มเข้าสู่ระบบ/สมัคร และข้อผิดพลาดภาษาอังกฤษ |
| Avatar Selection | ชุดรูปตัวละครพิกเซลให้เลือกและภาพตัวอย่างของตัวเอง ไม่มีการอัปโหลด |
| Chat | แท็บ World/Guild/Private รายการห้อง ชื่อห้อง ข้อความของห้องที่เลือก ช่องพิมพ์ และรายชื่อผู้เล่นด้านข้าง |
| Guild Directory | ชื่อกิลด์ คำอธิบาย เจ้าของ รายชื่อสมาชิก Join สำหรับกิลด์ที่ยังไม่เข้าร่วม และ Open สำหรับกิลด์ที่เป็นสมาชิก |
| Create Guild | ชื่อกิลด์ คำอธิบาย และปุ่ม Create เริ่มต้นมีผู้สร้างคนเดียว |
| Guild Management | Leave สำหรับสมาชิก และ Transfer Ownership / Disband สำหรับเจ้าของ |
| Private | เลือกผู้เล่นเพื่อเปิดห้องคู่สนทนา แยกรายการห้องและจำนวนยังไม่อ่านของแต่ละคู่ |

ข้อเสนอการจัดหน้าจอคอมพิวเตอร์: แถบบนเป็นข้อมูลตัวเองและสถานะเชื่อมต่อ ใต้ลงมาเป็นแท็บชนิดช่อง รายการห้องอยู่ทางซ้าย พื้นที่ข้อความตรงกลาง และผู้เล่นออนไลน์ทางขวา โดย World สามารถมีรายการห้องเพียงรายการเดียวได้

ข้อเสนอมือถือ: แสดงพื้นที่แชทเป็นหน้าหลัก เปิดรายการห้องและผู้เล่นผ่านแผงพับหรือ drawer ยังคงเข้าถึง World/Guild/Private, Guild Directory, การจัดการกิลด์ และการออกจากระบบได้ โดยไม่ต้องเลื่อนหน้าทั้งหน้าในแนวนอน

### 4.6 กติกาการโต้ตอบที่เสนอ

- เมื่อเปิดห้องใหม่ แสดงสถานะโหลดก่อนประวัติ และไม่แสดงข้อความของห้องเดิมใต้ชื่อห้องใหม่
- ตัวเลขยังไม่อ่านแยกตามห้อง รวมถึงแยกแต่ละกิลด์และแต่ละคู่สนทนา การเปลี่ยนแท็บไม่ถือว่าอ่านทุกห้องในแท็บนั้นแล้ว
- รายชื่อผู้เล่นออนไลน์รวมตัวเอง แต่ไม่ให้เริ่ม Private กับตัวเอง กดคนอื่นเพื่อเปิดห้องเดิมหรือสร้างบทสนทนาคู่ใหม่
- ถ้ายังไม่เข้าร่วม World/Guild แสดงปุ่ม Join และข้อมูลห้อง โดยไม่แสดงข้อความหรือเปิดช่องส่งก่อนเข้าร่วม
- Enter เพื่อส่งใช้เมื่อไม่ได้กำลังเลือกอักขระผ่าน IME เพื่อให้พิมพ์ภาษาไทยหรือภาษาอื่นได้ตามปกติ มือถือมีปุ่ม Send ให้กดชัดเจน
- อีโมจิเป็นข้อความ Unicode ส่วนปุ่มเลือกอีโมจิและรูปแบบรายการสามารถกำหนดระหว่างออกแบบภาพได้ ยังไม่รวมสติกเกอร์หรือแนบไฟล์
- แยกสถานะ Connecting, Connected, Reconnecting และ Send failed ให้ผู้ใช้เข้าใจ และไม่ล้างข้อความร่างเมื่อส่งล้มเหลว
- รูปพิกเซลเป็นชุดภาพที่ออกแบบสำหรับโปรเจกต์ อิงอารมณ์ย้อนยุคที่เลือกไว้ โดยยังไม่ตัดสินใจจำนวนตัวละครหรือชื่ออาชีพ

### 4.7 ขอบเขตการคุยในช่วงนี้

ช่วงวางแผนเคยพักเรื่องฐานข้อมูล โฮสต์ และ AI เพื่อคุย UI/UX หลังจากนั้นคุยเพิ่มเรื่อง Vercel และ OpenRouter และผู้ใช้ให้เริ่มสร้างแล้ว ใช้ SQLite ตามเดิม เตรียม AI ผ่าน OpenRouter โมเดลฟรี และยังไม่ถือว่าเลือกหรือสมัครโฮสต์ออนไลน์แทนผู้ใช้

## 5. สถาปัตยกรรมที่เสนอ

```text
คอมพิวเตอร์ A: Browser ── HTTPS + WSS ──┐
                                       ├── โฮสต์บนอินเทอร์เน็ต ── Node.js Server
คอมพิวเตอร์ B: Browser ── HTTPS + WSS ──┘                              │
                                                                     ├── ฐานข้อมูลถาวร
                                                                     └── AI Provider
```

ระบบใช้งานจริงให้เซิร์ฟเวอร์อยู่บนโฮสต์ที่เข้าถึงได้จากอินเทอร์เน็ต ทุก client เชื่อมต่อ URL เดียวกัน สำหรับพัฒนาในเครื่องยังเปิด localhost หรือทดลอง LAN ได้ แต่ไม่ใช่เป้าหมายส่งมอบเพียงอย่างเดียว

| ส่วน | เทคโนโลยีที่เสนอ | หน้าที่ |
| --- | --- | --- |
| หน้าเว็บ | React + TypeScript + Vite | หน้าล็อกอิน หน้าต่างแชท และการจัดการสถานะบนจอ |
| เซิร์ฟเวอร์ | Node.js + ไลบรารี ws | ยืนยันตัวตน ตรวจสิทธิ์ห้อง และรับส่งข้อความ |
| ฐานข้อมูลเริ่มต้น | SQLite บนเครื่องเซิร์ฟเวอร์ | เก็บบัญชี session ห้อง สมาชิก และประวัติ |
| บริการ AI | ผู้ให้บริการที่รองรับ API ที่เลือก | ฟีเจอร์ AI ที่จะตกลงภายหลัง |

HTTPS ใช้โหลดหน้าเว็บและจัดการบัญชี ส่วน WSS เป็น WebSocket ที่เข้ารหัส ใช้รับส่งข้อความและเหตุการณ์แชทแบบสองทาง โดย WebSocket ทำงานบน TCP การเข้ารหัส TLS เป็นส่วนของการติดตั้งใช้งานจริงตั้งแต่เวอร์ชันแรก ส่วน HTTP/WS ใช้สำหรับพัฒนาในเครื่อง

ผู้ใช้ยืนยันใช้ SQLite แล้ว เก็บไฟล์ฐานข้อมูลไว้ฝั่งเซิร์ฟเวอร์ และ client ทุกเครื่องใช้ข้อมูลร่วมกันผ่านเซิร์ฟเวอร์ ไม่ได้มีฐานข้อมูลแยกในแต่ละเบราว์เซอร์ การเลือก SQLite ไม่ได้ยกเลิกเป้าหมายเข้าใช้งานผ่านอินเทอร์เน็ต

### 5.1 ข้อกำหนดการติดตั้งบนอินเทอร์เน็ต

สิ่งที่ต้องจัดเตรียมสำหรับส่งมอบ:

- โฮสต์ที่รัน Node.js server และรับการเชื่อมต่อ WebSocket ได้ ไม่ใช่พื้นที่ฝากไฟล์หน้าเว็บอย่างเดียว
- URL ที่เข้าถึงได้จากภายนอก พร้อม TLS certificate สำหรับ HTTPS/WSS อาจใช้โดเมนที่ผู้ให้บริการมีให้ก่อน โดยยังไม่จำเป็นต้องซื้อชื่อโดเมนเอง
- พื้นที่ข้อมูลถาวรและวิธีสำรองข้อมูลสำหรับ SQLite ให้เริ่มด้วย app instance เดียวและเก็บไฟล์บนดิสก์ถาวรของเครื่องเซิร์ฟเวอร์หรือ persistent volume ที่รองรับการใช้งาน SQLite ไม่เลือกโฮสต์ที่ทำให้ไฟล์ฐานข้อมูลหายเมื่อ restart/deploy
- เสิร์ฟหน้าเว็บ API และ /socket ภายใต้ origin เดียวกัน เพื่อลดความซับซ้อนของ cookie และการตรวจ origin
- ตั้ง reverse proxy ให้ส่งต่อการเชื่อมต่อ WebSocket และเปิดใช้ Secure session cookie บน HTTPS
- เก็บค่าลับไว้ใน environment/secrets ของโฮสต์ และแยกฐานข้อมูลพัฒนากับฐานข้อมูลใช้งานจริง
- กำหนดวิธี restart/deploy โดยรักษาข้อมูล และให้หน้าเว็บเชื่อมต่อใหม่พร้อมโหลดข้อความที่ขาดหลังเซิร์ฟเวอร์เริ่มใหม่

ยืนยันฐานข้อมูลเป็น SQLite แล้ว และต้องการสำรวจบริการฟรีก่อน ยังไม่ได้เลือกโฮสต์หรือแพ็กเกจ และยังไม่มีการสมัครบริการ ชำระเงิน หรือนำโค้ดขึ้นใช้งานจริงในขั้นวางแผนนี้

### 5.2 ผลสำรวจตัวเลือกฟรี

ตรวจสอบเอกสารผู้ให้บริการเมื่อ 2 พฤศจิกายน 2026 รายละเอียดและโควตาอาจเปลี่ยนได้ ดูผลเปรียบเทียบและแหล่งข้อมูลใน [HOSTING.md](HOSTING.md)

เคยเสนอ Render Free คู่กับ Neon Free สำหรับ PostgreSQL แต่ข้อเสนอนี้ถูกแทนที่ด้วยการตัดสินใจใช้ SQLite จึงไม่ใช่แนวทางที่จะนำไปพัฒนาต่อ

ผลต่อระบบ: คง storage layer แบบ SQLite และออกแบบการสำรองข้อมูล ผู้ใช้ขอให้หาโฮสต์ฟรีโดยไม่ใช้บัตร จึงตัด alwaysdata ออกจากตัวเลือกหลักเพราะขั้นตอนยืนยันบัตรยังไม่สอดคล้องเงื่อนไข พบ Weeny และ Wispbyte เป็นตัวเลือกสำหรับทดสอบ แต่ยังไม่ได้ยืนยันการรับบัญชีฟรี WSS และความถาวรของข้อมูลจากการ deploy จริง ดู [HOSTING.md](HOSTING.md)

Render Free ไม่เหมาะกับการเก็บไฟล์ SQLite ถาวรตามผลสำรวจ ระบบยังต้องแสดงสถานะ reconnect และไม่แสดงว่าส่งข้อความสำเร็จก่อนเซิร์ฟเวอร์ตอบรับ งบ AI แยกจากโฮสต์และฐานข้อมูล ยังไม่ได้เลือกผู้ให้บริการ AI

## 6. โครงสร้างข้อมูลเบื้องต้น

| ข้อมูล | ฟิลด์หลัก | ข้อกำหนด |
| --- | --- | --- |
| users | id, name, password_hash, created_at | ชื่อไม่ซ้ำ ไม่เก็บรหัสผ่านเป็นข้อความธรรมดา |
| sessions | token_hash, user_id, expires_at | session มีวันหมดอายุและเพิกถอนได้ |
| rooms | id, name, kind, description, owner_id, private_pair | kind เป็น world / guild / private |
| members | room_id, user_id | สมาชิกคนเดียวไม่ซ้ำในห้องเดียวกัน |
| messages | id, sequence, room_id, user_id, text, created_at | เรียงข้อความและแบ่งโหลดประวัติได้ |

ชื่อฟิลด์ในตารางนี้ใช้สื่อความหมาย ไม่ใช่สัญญาว่าชื่อต้องตรงกับโค้ดร่างทุกตัว

ห้อง Private ของบัญชีคู่เดิมควรใช้ห้องเดิมเสมอ และผูกกับ user ID แทนชื่อที่แสดง ข้อมูลสมาชิกและสิทธิ์ทั้งหมดให้เซิร์ฟเวอร์เป็นผู้ตัดสิน ไม่อาศัยการซ่อนปุ่มบนหน้าเว็บเพียงอย่างเดียว

## 7. เหตุการณ์ผ่าน WebSocket ที่เสนอ

| คำขอ/เหตุการณ์ | ใช้ทำอะไร |
| --- | --- |
| state | ส่งรายการห้อง สมาชิก และสถานะออนไลน์ที่บัญชีนั้นมีสิทธิ์เห็น |
| join | ผู้ใช้ขอเข้าร่วม World หรือ Guild ด้วยตัวเอง |
| createGuild | สร้างกิลด์และเพิ่มเฉพาะผู้สร้าง |
| private | เปิดหรือค้นหาห้องส่วนตัวของบัญชีคู่หนึ่ง |
| history | ขอข้อความเก่าในห้องที่มีสิทธิ์ |
| message | ส่งข้อความและกระจายไปยังผู้มีสิทธิ์ในห้อง |
| typing | แจ้งว่ามีผู้กำลังพิมพ์ เป็นฟีเจอร์ที่เลือกแล้ว |
| reply | ตอบผลสำเร็จหรือข้อผิดพลาดของคำขอ |

ต้องออกแบบเหตุการณ์เพิ่มสำหรับออกจากกิลด์ โอนเจ้าของ ยุบกิลด์ ค้นหาข้อความ และบันทึกตำแหน่งอ่านล่าสุด โดยโค้ดร่างปัจจุบันยังไม่มีส่วนเหล่านี้

แต่ละคำขอควรมี request ID เพื่อจับคู่คำตอบ การเชื่อมต่อใหม่ต้องโหลดสถานะและข้อความที่ตกหล่น และหน้าเว็บต้องไม่แสดงว่าส่งสำเร็จก่อนเซิร์ฟเวอร์ตอบรับ

### 7.1 API บัญชีและ API ภายนอก

API หลักเป็น API ที่สร้างเองในเซิร์ฟเวอร์ของโปรเจกต์ ไม่ได้ใช้บริการแชทสำเร็จรูป เช่น Firebase หรือบริการแชทของ Discord

| HTTP API ในโค้ดร่าง | หน้าที่ |
| --- | --- |
| POST /api/register | สมัครสมาชิกและสร้าง session |
| POST /api/login | ตรวจรหัสผ่านและสร้าง session |
| GET /api/me | ตรวจบัญชีจาก session ปัจจุบัน |
| POST /api/logout | เพิกถอน session และตัดการเชื่อมต่อของ session นั้น |
| GET /api/health | ตรวจว่าเซิร์ฟเวอร์ตอบสนอง |
| POST /api/summary | ขอ AI สรุปข้อความในห้องที่ผู้ขอเป็นสมาชิก ถ้าตั้งค่าผู้ให้บริการแล้ว |

ส่วนข้อความแชทใช้ WebSocket ที่ /socket: หน้าเว็บใช้ WebSocket API ของเบราว์เซอร์ และเซิร์ฟเวอร์ใช้ไลบรารี ws โดยมี action ตามตารางในหัวข้อ 7 ไม่ใช้ HTTP API เป็นช่องทางส่งข้อความแชท

API ภายนอกมีเฉพาะส่วน AI หากเลือกเปิดใช้ โค้ดร่างเตรียมการเชื่อมต่อรูปแบบ OpenAI-compatible Chat Completions ไว้ แต่ยังไม่มี API key และโมเดลที่เลือก จึงยังใช้งาน AI จริงไม่ได้ และส่วนนี้ยังเปลี่ยนได้ตามข้อสรุป

### 7.2 ลำดับการส่งข้อความในโค้ดร่าง

1. หน้าเว็บล็อกอินผ่าน HTTP และรับ session cookie แบบ HttpOnly
2. หน้าเว็บเปิด WebSocket ไปยัง /socket เซิร์ฟเวอร์ตรวจ origin และ session ก่อนรับการเชื่อมต่อ
3. เซิร์ฟเวอร์ส่งรายการห้องและรายชื่อผู้ใช้ที่บัญชีนั้นมีสิทธิ์เห็น
4. เมื่อส่งข้อความ client ระบุ roomId และเนื้อหา เซิร์ฟเวอร์ใช้ตัวตนจาก session ไม่เชื่อชื่อผู้ส่งที่ client อ้างเอง
5. เซิร์ฟเวอร์ตรวจสิทธิ์สมาชิก ขนาดข้อความ และความถี่คำขอ
6. บันทึกข้อความใน SQLite ก่อนตอบรับว่าส่งสำเร็จ
7. ส่งเหตุการณ์ข้อความไปยังการเชื่อมต่อที่เป็นสมาชิกห้องนั้นเท่านั้น รวมผู้ส่ง เพื่อให้หลายแท็บของบัญชีเดียวกันรับข้อมูลได้
8. เมื่อต้องการประวัติ client ขอ history เซิร์ฟเวอร์ตรวจสมาชิกและแบ่งส่งครั้งละไม่เกิน 50 ข้อความ

ข้อความที่บันทึกแล้วสามารถขออ่านใหม่ได้ แต่โค้ดร่างยังไม่มี client message ID สำหรับกันข้อความซ้ำจากการลองส่งใหม่หลังเครือข่ายขาด ต้องออกแบบส่วน reconnect และ retry ให้ครบก่อนพัฒนาหน้าเว็บ

## 8. บัญชีและความเป็นส่วนตัว

- แยก user ID ถาวรออกจากชื่อที่แสดง
- เก็บรหัสผ่านด้วย password hashing พร้อม salt
- ใช้ session cookie แบบ HttpOnly และจำกัด origin ของคำขอ/การเชื่อมต่อ
- ตรวจสอบสิทธิ์ห้องทุกครั้งที่ขอประวัติหรือส่งข้อความ
- ยกเลิก session เมื่อออกจากระบบ และตัด WebSocket ของ session นั้น
- จำกัดความยาวข้อความและความถี่คำขอ เพื่อป้องกันการส่งถี่ผิดปกติ
- แสดงข้อความเป็นข้อความธรรมดา ไม่แทรก HTML จากผู้ใช้
- เก็บ API key ฝั่งเซิร์ฟเวอร์ และไม่ส่งไปกับหน้าเว็บหรือ commit ลง Git

ระบบนี้ยังไม่ได้ออกแบบการเข้ารหัสแบบ end-to-end เซิร์ฟเวอร์และผู้ที่เข้าถึงฐานข้อมูลสามารถอ่านข้อความที่จัดเก็บได้

## 9. ฟีเจอร์พิเศษที่เลือกแล้ว

ผู้ใช้เลือกฟีเจอร์ต่อไปนี้สำหรับขอบเขตงานเพิ่มเติม การนับเป็นคะแนนพิเศษแต่ละข้อยังขึ้นกับการประเมินของอาจารย์

| ฟีเจอร์ | ประโยชน์ | สิ่งที่ต้องเตรียมเพิ่ม |
| --- | --- | --- |
| AI สรุปแชท | สรุปสิ่งที่คุยกันในห้อง | โมเดล/ผู้ให้บริการ, API key หรือโมเดลที่รันเอง |
| สถานะกำลังพิมพ์ | เห็นว่าคู่สนทนากำลังตอบ | ไม่ต้องใช้บริการภายนอก |
| จำนวนข้อความยังไม่อ่าน | ตามบทสนทนาได้ง่าย | ออกแบบตำแหน่งอ่านล่าสุด |
| ค้นหาข้อความ | หาข้อความเก่า | กำหนดขอบเขตและสิทธิ์การค้นหา |

แนวทางรายละเอียดที่เสนอ:

- AI สรุปแชท: ผู้ใช้กดสรุปในห้องที่มีสิทธิ์อ่าน ส่งข้อความล่าสุดจำนวนจำกัดไปยังโมเดล และแสดงผลแยกจากข้อความของผู้เล่น ไม่เรียก AI ทุกครั้งที่มีข้อความใหม่
- ค้นหาข้อความ: ค้นหาบนเซิร์ฟเวอร์ภายในห้องที่กำลังเปิด โดยตรวจสิทธิ์ก่อนและแบ่งหน้าผลลัพธ์ ไม่จำกัดแค่ข้อความที่โหลดไว้ในเบราว์เซอร์
- ข้อความยังไม่อ่าน: เพิ่มข้อมูลตำแหน่งอ่านล่าสุดต่อบัญชีต่อห้องในฐานข้อมูล เพื่อให้ยังถูกต้องหลังรีเฟรชหรือเปลี่ยนเครื่อง ไม่นับข้อความที่ตนเองส่งเป็นข้อความยังไม่อ่าน
- กำลังพิมพ์: ส่งเป็นเหตุการณ์ชั่วคราวเฉพาะสมาชิกห้อง ไม่บันทึกลงฐานข้อมูล และซ่อนสถานะอัตโนมัติเมื่อหยุดพิมพ์หรือหลุดการเชื่อมต่อ

AI แปลภาษา รูปอัปโหลด และสติกเกอร์ยังไม่อยู่ในขอบเขตที่เลือก ระบบที่สร้างเตรียมใช้ OpenRouter โมเดลฟรี โดยผู้ใช้สอบถามและได้รับคำอธิบายข้อจำกัดแล้ว ให้สมาชิกยินยอมก่อนเรียกสรุปจากห้องที่มีสิทธิ์ และยังต้องใส่ key จริงก่อนทดสอบผู้ให้บริการ

## 10. สถานะโค้ดปัจจุบัน

- มีหน้า React/TypeScript ธีมพิกเซล พร้อมรูปตัวละคร 6 แบบและหน้าจอ responsive
- สมัคร/ล็อกอิน เปลี่ยนรูป ออกจากระบบ และแสดงออนไลน์ผ่าน WebSocket ได้
- World และ Guild เข้าร่วมเอง มีห้อง Private เฉพาะคู่
- กิลด์สร้าง เข้าร่วม ออก โอนเจ้าของ และยุบแบบ archive ได้
- มีค้นหาประวัติแบบแบ่งหน้า unread แบบเก็บถาวร typing และการเชื่อมต่อใหม่/กันข้อความซ้ำ
- มี SQLite พร้อม schema migration เบื้องต้นและคำสั่ง backup
- เตรียมสรุปแชทผ่าน OpenRouter โมเดลฟรี มี consent, cache และการรับมือ quota/error ยังไม่เรียก provider จริง
- มี README, Dockerfile และตัวอย่าง reverse proxy สำหรับติดตั้งภายหลัง Docker image ผ่าน build และ smoke test พร้อม SQLite backup/restart แล้ว
- build และ 15 กลุ่มทดสอบผ่าน รวม 9 บัญชีพร้อมกัน ตรวจ UI สองบัญชี desktop/mobile และ HTTP ผ่าน IP ของ Wi-Fi แล้ว
- ยังไม่ deploy ออนไลน์หรือทดสอบคนละคอมพิวเตอร์จริง การตรวจ 9 บัญชียังเป็น baseline ในเครื่องเดียว

รายละเอียดเล็กน้อยที่ไม่ได้ยืนยันใช้ค่าเริ่มต้นตามข้อเสนอ เช่น ยุบกิลด์แล้ว archive ประวัติและปิดสิทธิ์ โดยระบุพฤติกรรมนี้ใน UI/README ชัดเจน ไม่ใช่การลบข้อมูลถาวร

## 11. เนื้อหาที่จัดทำใน README

1. ภาพรวมระบบ เทคโนโลยี และความต้องการของเครื่อง
2. วิธีติดตั้ง เปิดโหมดพัฒนา build และเปิดใช้งาน
3. วิธีตั้งค่า .env พร้อมคำอธิบายแต่ละตัวแปร
4. ที่เก็บฐานข้อมูล วิธีสำรอง และการเก็บข้อมูลเมื่อย้ายเครื่อง
5. วิธีเปิดใช้งานจากคอมพิวเตอร์อย่างน้อยสองเครื่องใน LAN รวมการตั้งค่า firewall ที่จำเป็น
6. วิธีสมัคร/ล็อกอิน และทดลอง World, Guild, Private
7. วิธีเชื่อมต่อ AI ถ้าเลือกใช้ พร้อมแจ้งค่าใช้จ่ายและการส่งข้อมูลภายนอก
8. วิธีทดสอบ ข้อจำกัด และแนวทางแก้ปัญหาที่พบบ่อย
9. ตารางเทียบ R1–R11 กับตำแหน่งโค้ดและขั้นตอนสาธิต
10. สิ่งที่ต้องเตรียมเพิ่มเติมเมื่อต้องการนำขึ้นใช้งานจริง เช่น โฮสต์ พื้นที่เก็บข้อมูลถาวร HTTPS และชื่อโดเมนถ้าต้องการ
11. ขั้นตอน deploy ผ่านอินเทอร์เน็ต ตั้งค่า HTTPS/WSS, Secure cookie, WebSocket proxy, สำรอง/กู้ข้อมูล และตรวจหลังอัปเดตระบบ โดยการออนไลน์เป็นขอบเขตเวอร์ชันแรกแล้ว

## 12. แผนตรวจรับที่เสนอ

- สมัครชื่อซ้ำไม่ได้ และล็อกอินด้วยรหัสผิดไม่ได้
- บัญชีที่ยังไม่ล็อกอินเปิด WebSocket และอ่านข้อความไม่ได้
- เปิดจากสองเครื่องแล้วเห็นรายชื่อออนไลน์รวมตัวเอง
- World และ Guild ต้องกดเข้าร่วมก่อนส่งหรืออ่านประวัติ
- กิลด์ใหม่มีผู้สร้างคนเดียว และผู้สร้างเพิ่มคนอื่นแทนไม่ได้
- ทุกคนดูรายการกิลด์และชื่อสมาชิกได้ โดยยังไม่เห็นข้อความห้องที่ไม่ได้เข้าร่วม
- สมาชิกใหม่เปิดอ่านประวัติกิลด์ก่อนเข้าร่วมได้ทั้งหมดหลังสมัครเข้ากิลด์สำเร็จ
- การออกและยุบกิลด์ทำงานตามกติกาที่ตกลง และเพิกถอนสิทธิ์ของการเชื่อมต่อที่เปิดอยู่
- โอนเจ้าของให้สมาชิกปัจจุบันได้ เฉพาะเจ้าของเดิมเท่านั้นที่ทำได้ และไม่เกิดเจ้าของสองคนหรือกิลด์ที่ไม่มีเจ้าของจากคำขอพร้อมกัน
- ใช้บัญชี A/B/C ตรวจว่า C ไม่ได้รับข้อความหรือประวัติ Private ของ A กับ B
- ตรวจสิทธิ์ห้องด้วยคำขอที่ดัดแปลงเอง ไม่ตรวจเฉพาะปุ่มบนจอ
- เปิดหลายแท็บ ออกจากระบบ และเชื่อมต่อใหม่แล้วสถานะออนไลน์ยังถูกต้อง
- ปิดและเปิดเซิร์ฟเวอร์ใหม่แล้วบัญชี ห้อง และประวัติยังอยู่
- ทดสอบฟีเจอร์ AI จริงหลังเลือกผู้ให้บริการและตั้งค่าแล้ว
- ค้นหาพบข้อความเก่าที่อยู่นอกหน้าประวัติที่โหลดไว้ โดยไม่เปิดเผยห้องที่ไม่มีสิทธิ์
- จำนวนยังไม่อ่านตรงกันเมื่อเปิดหลายแท็บหรือรีเฟรช และสถานะกำลังพิมพ์หายเมื่อหยุดหรือหลุด
- UI และข้อผิดพลาดเป็นภาษาอังกฤษ โดยยังส่งและแสดงข้อความภาษาไทยได้
- แสดงเฉพาะข้อความห้องที่เลือก ตัวเลขยังไม่อ่านแยกห้อง และไม่ปะปนข้อความระหว่างสลับห้อง
- เลือกรูปตัวละครได้จากชุดที่เตรียมไว้ โดยไม่มีเส้นทางอัปโหลดรูปหรือตรากิลด์ในเวอร์ชันแรก
- รายการกิลด์แสดงข้อมูลครบและ Join/Open เปลี่ยนตามสถานะสมาชิก
- Enter ส่ง Shift+Enter ขึ้นบรรทัดใหม่ และการเลือกอักขระด้วย IME ไม่ส่งข้อความโดยไม่ได้ตั้งใจ
- ใช้งานบนคอมพิวเตอร์และมือถือได้ รวมการเปิดห้อง รายชื่อผู้เล่น การส่งข้อความ และการจัดการกิลด์
- เปิด URL จริงจากคอมพิวเตอร์อย่างน้อยสองเครื่องผ่านอินเทอร์เน็ต แล้วล็อกอินและสนทนาร่วมกันได้
- หน้าเว็บใช้ HTTPS และแชทใช้ WSS พร้อม session cookie แบบ Secure
- restart และ deploy ใหม่แล้วบัญชี ห้อง และข้อความในระบบออนไลน์ยังอยู่

## 13. คำถามสำหรับคุยต่อ

คุยทีละข้อแล้วนำคำตอบมาอัปเดตเอกสารนี้ ไม่จำเป็นต้องตอบทั้งหมดพร้อมกัน

1. วันส่งงานหรือวันสาธิตยังไม่ได้ระบุ ผู้ใช้ยืนยันจำนวนออนไลน์พร้อมกันไม่ถึง 10 คนแล้ว
2. พักไว้ก่อน: ต้องยืนยันตัวเลือกโฮสต์ด้วยการสมัคร/ทดสอบเมื่อถึงขั้นติดตั้ง โดยรักษาเงื่อนไขฟรี ไม่ใช้บัตร และ SQLite ถาวร ไม่เลือกแพ็กเกจเสียเงินแทนหากโควตาฟรีเต็ม
3. พักไว้ก่อน: ทดสอบและเลือกโมเดลสรุปแชทบน AI Free tier ตามที่ผู้ใช้ขอ ไม่ต้องส่ง API key ในแชท
4. เมื่อยุบกิลด์ ต้องการลบประวัติถาวรหรือเก็บเป็นข้อมูลที่ปิดใช้งานยังไม่ได้ตอบตรง ๆ ข้อเสนอเริ่มต้นคือเก็บข้อมูลและปิดการเข้าถึง ส่วนระบบโอนเจ้าของได้รับการยืนยันแล้ว
5. ผู้ใช้ให้เริ่มพัฒนาแล้ว ใช้ผลตรวจใน VALIDATION.md เป็นสถานะงาน และแยกส่วนที่ยังไม่ทดสอบกับบริการจริงออกจากส่วนที่ตรวจในเครื่องแล้ว

รายละเอียดภาพและตำแหน่งปุ่มสามารถเสนอเป็นแบบร่างตามแนว Ragnarok ได้ต่อไป โดยไม่ต้องถามซ้ำเรื่องเกมต้นแบบ ภาษา บัญชี ประวัติกิลด์ หรือชุดฟีเจอร์ที่ผู้ใช้ตอบแล้ว
